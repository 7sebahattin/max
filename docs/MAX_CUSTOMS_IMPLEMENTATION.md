# MAX Customs 0.1 — local declaration drafts

Issue #26. Standalone optional external module for pinned Dolibarr 24.0.1. No dependency on any unmerged MAX branch. No core changes, native commercial writes, government filing, HKS, SMTP or external API. All approvals/statuses are **local and unsubmitted**, not regulatory acceptance.

## Setup and use

Install `modules/maxcustoms` under `htdocs/custom/maxcustoms` or use the source-only module ZIP generated by CI. Enable it with native module administration. Prototype ID 610160 and rights 61016001–61016009 have a collision guard; public registry/commercial licensing review is not implied.

Grant native MAX Customs view/create/edit/status/match/contact/analysis/source/admin rights as needed. Internal users also need native third-party read, all-customer visibility, order read and shipment read. This conservative first slice does not certify assigned-customer-only visibility and does not grant native rights automatically. External users are denied. MAX admin is explicitly privileged across module sections, while ordinary view does not grant sensitive access.

Create a draft with reference and manual public fields. Edit while draft; a version check rejects stale writes. A matcher enters existing customer/order IDs, exact customer/native order reference and zero-to-many shipment IDs and explicitly confirms. The native Societe/Commande/Expedition APIs verify installation, customer, order reference and each shipment's native origin. No inferred quantities or shipment changes occur.

A status operator can move draft → reviewed → approved → closed. Required local context and a confirmed native order link are needed for review. Unreadable evidence blocks review until a source-authorized status operator explicitly acknowledges it as opaque. This is not extraction/fact approval. Corrections from reviewed/approved to draft require module admin and confirmation. Draft/reviewed cancellation requires status permission; approved cancellation requires admin; closed/cancelled are terminal in this slice.

## Privacy matrix and server boundaries

| Capability | Required rights in addition to view/native read scope |
|---|---|
| Create | create |
| Edit public data while draft | edit |
| Change status | status; guarded corrections additionally admin |
| Confirm native associations | match |
| Read contact/driver notes | contact |
| Read product analysis | analysis |
| Read raw source / private evidence download | source |
| Modify a restricted section | edit AND the corresponding contact/analysis/source permission |
| Add private text evidence | edit AND source |
| Acknowledge unreadable evidence | status AND source |

The model's single projection function drives HTML, JSON API and CSV exports. General reads never select restricted columns. Unauthorized fields are omitted, not CSS-hidden or serialized as hidden inputs. Sensitive history categories are also omitted. Unauthorized update/clearing attempts are rejected before data validation. Audit rows contain actor/time/action/field/status, never source/contact/analysis content. API writes use form-encoded native CSRF tokens; JSON GET is a session-authenticated projection, not a public integration.

Evidence is outside webroot, private-directory 0700/file 0600, server-generated filenames, bounded to 8 KiB `.txt` files with detected text/plain or opaque octet-stream. Invalid UTF-8/NUL evidence remains needs_review. It never populates fields. Upload replay uses an entity/declaration/content-hash unique key. Downloads require source permission and integrity checks, force attachment/octet-stream, and set nosniff/sandbox headers. Broad PDF uploads/parsing are **NOT IMPLEMENTED**; unsupported MIME/size/name is rejected without storage. CSV formula prefixes, including leading whitespace/BOM, are neutralized. No official customs document template is claimed.

## Storage, tests and rollback

Five MAX-owned tables hold drafts/public metadata, separated restricted fields, native shipment references, append-only history and immutable evidence metadata. Creation uses Dolibarr's supported `_init` SQL-array lifecycle (repository policy forbids standalone SQL dumps). MariaDB 11.4 is tested; PostgreSQL is **NOT CERTIFIED**. Disabling removes native menus/rights and denies access while preserving module data/files. Re-enable restores access; no native record migration or historical data import occurs.

Run in a fresh checkout with generated disposable `.env`, Docker, Python and Playwright 1.56.0/Chromium:

```sh
python3 -m unittest discover -s tests/customs -v
COMPOSE_PROJECT_NAME=max-customs-unique bash scripts/customs_test.sh
```

The runner refuses pre-existing labeled containers, volumes or networks before arming cleanup, invokes unchanged main P2/native installation in its own project, then tests module lifecycle, role matrix, redaction/update denial, private evidence, zero/one/many native partial shipment links, state history/correction, stale edits, entity isolation, native ERP/legal snapshots, native HTTP/CSRF and 18 strict 360/390/768 renders. Only public-role screenshots and numeric reports/source ZIP are artifacts. Native fake fixture operations happen before the customs-only snapshot boundary. No private field values, passwords, raw evidence or installer/config output may be published.

Full local Docker integration is **BLOCKED** by managed 8 GB/vfs storage; actual native installation runs in disposable GitHub Actions. Failed runs and exact-SHA evidence are recorded in the draft PR and below when available. Existing doctor/source-policy/MAX Core tests remain unchanged. This independent branch does **not** certify co-enabled whole-product integration (Issue #20).

Rollback: disable the module, preserving drafts/history/private evidence. Discarding the owned CI project removes only its synthetic data. HKS draft mapping/button, customs-government EDI, VAT/e-filing, PDF parsing, automatic financial/stock/order effects and live deployment are **NOT IMPLEMENTED**. Exact regulatory fields/templates and production role policy remain owner review decisions.
